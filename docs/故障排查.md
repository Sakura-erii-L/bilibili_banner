# 故障排查

先确认问题发生在抓取、构建还是浏览器展示阶段。抓取失败通常查看终端日志和 `data/diagnostic.json`；展示失败通常查看 `_site/data/index.json` 和对应 manifest。

## 1. Python 或 Playwright 未安装

典型错误：

```text
ModuleNotFoundError: No module named 'playwright'
```

在项目根目录执行：

```bash
python -m pip install -r requirements.txt
```

Windows 如果 `python` 不可用，可使用：

```powershell
py -3 -m pip install -r requirements.txt
```

## 2. 找不到浏览器或浏览器启动失败

抓取器优先寻找系统 Edge/Chrome/Chromium；找不到时使用 Playwright 管理的 Chromium。没有系统浏览器时执行：

```bash
python -m playwright install chromium
```

如果浏览器安装在非标准位置，可设置：

```powershell
$env:BROWSER_EXE = 'C:\path\to\msedge.exe'
python backend\capture.py
```

Linux/NAS 示例：

```bash
export BROWSER_EXE=/usr/bin/chromium
python backend/capture.py
```

`BROWSER_EXE` 必须指向存在的可执行文件；否则程序会继续自动探测。

### 2.1 GitHub Action 安装 Chromium 失败

先打开失败运行，确认失败 step 是 `Install Playwright Chromium`，而不是 `Capture current Bilibili banner`。工作流使用：

```bash
python -m playwright install --with-deps chromium
```

处理顺序：

1. 点击 `Re-run failed jobs`，排除临时下载或 Ubuntu 软件源故障。
2. 确认 workflow 没有被改到 Windows runner；当前命令按 `ubuntu-latest` 编写。
3. 确认 `Install Python dependencies` 已成功，且 `requirements.txt` 中的 Playwright 安装完成。
4. 如果仍失败，展开日志记录具体的下载 URL、apt 错误或磁盘空间错误；不要通过设置 `BROWSER_EXE` 指向本地电脑路径来修复 GitHub Runner。

程序不要求 Runner 预装系统 Chrome；Playwright Chromium 安装成功后会使用它，并始终以 headless 模式运行。

## 3. 找不到 `.animated-banner`

典型错误：

```text
No .animated-banner was found. See data/diagnostic.json
```

检查：

1. 是否可以在同一台机器访问 `https://www.bilibili.com/`。
2. 页面是否返回验证码、错误页、登录拦截页或其他重定向。
3. `data/diagnostic.json` 中的 `url`、`title`、`animatedCount`、`layerCount`。
4. 是否设置了错误的 `BANNER_SOURCE_URL`。

当前程序接受 `.animated-banner`、`.bili-header__banner`、`.head-banner`、`.bili-banner` 等支持容器。所有候选都不存在时才视为错误页面。

## 4. 运动量为零或交互参数缺失

典型 manifest 状态：

```text
"interaction": {"model": "bilibili-sampled-horizontal-v1", "effects": []}
"completeness": "partial"
```

这表示探测后所有成功读取的图层都满足：

```text
interaction.effects 为空
```

优先检查：

- `data/diagnostic.json` 的 `before` 和 `after` 是否有差异。
- Bilibili 是否改变了运动元素位置，当前程序读取的是 `.layer.firstElementChild` 的 transform。
- 页面是否在探测期间仍未完成初始化。
- 当前视口是否触发了不同的 Banner 结构。

不要手写统一运动系数伪造交互。保留真实图层并标记 partial，待以后从 source 证据或其它归档来源恢复。

## 5. 图层资源下载失败

日志可能出现：

```text
Layer 3 asset download failed: ... See data/diagnostic.json
```

程序会保存已恢复图层并写入 `completeness: partial` 与 `missing_assets`，不会把部分下载失败伪装成 `static` 模式。检查：

- CDN URL 是否可访问。
- 是否需要保留 `Referer` 和 User-Agent；程序已按当前来源发送。
- 是否存在临时网络故障或 Bilibili CDN 限流。
- `data/diagnostic.json` 中的 `reason`、`before` 和 `after`。

如果需要重试，直接重新运行抓取即可。不要手工把远程 URL 写成前端资源，因为发布站点必须使用本地文件。

## 6. 同一日期没有新增历史记录

这是正常的去重行为，常见日志：

```text
No visual change: <contentHash>
```

或：

```text
Visual already exists in history; archive and current update skipped: <contentHash>
```

检查 `data/current/banner.json` 和 `data/index.json` 的 `contentHash`。当前内容相同或历史内容再次出现时，`data/` 完全不变，因此 GitHub Actions 也不会产生无意义 commit。

只有确实需要重新测量并刷新已有素材的交互元数据时才使用：

```bash
python backend/capture.py --force
```

`--force` 不会增加相同素材的物理归档；`contentHash` 相同时仍更新原 manifest。

## 7. 索引记录重复或旧数据异常

只重建索引，不重新访问 Bilibili：

```bash
python backend/capture.py --rebuild-index
```

该命令会扫描 `data/archive/*/banner.json`，按 `capturedAt` 倒序，并按 `contentHash` 去重。它不会删除重复目录，也不会修改 `data/current/`。

如果某个归档缺少 `banner.json` 或 JSON 损坏，索引会跳过该目录；先备份目录，再修复或移走异常文件。

## 8. 页面显示 404 或没有记录

检查构建前源数据：

```text
data/index.json
data/archive/<id>/banner.json
```

然后重新构建：

```bash
python scripts/build_site.py
```

本地预览不要双击 `index.html` 使用 `file://`，应运行：

```bash
python scripts/serve.py
```

再打开 <http://127.0.0.1:8765>。如果是 GitHub Pages，确认仓库设置为：

```text
Settings → Pages → Source → GitHub Actions
```

## 9. 页面加载失败或显示“分层素材载入失败”

前端会对每个 manifest 使用 `fetch()`，并在加载失败时直接显示错误。它不会使用 `preview.png`。

检查浏览器开发者工具和发布目录：

1. `_site/data/index.json` 的 `manifest` 是否存在。
2. 对应 `_site/data/archive/<id>/banner.json` 是否存在。
3. `banner.json` 中的 `file` 是否都能在同目录找到。
4. 是否只重新上传了 `frontend/` 而遗漏了 `data/`。
5. GitHub Pages 是否仍在部署旧版本；完成部署后强制刷新。

## 10. Banner 位置错位

当前前端会恢复每层初始 matrix、尺寸、`objectFit` 和 `objectPosition`，并在宽屏上按抓取视口进行补偿。排查顺序：

1. 对比当前归档的 `banner.json` 中 `viewport`、`banner`、`transform`。
2. 检查图层本地文件是否完整、是否被 CDN 错误页替代。
3. 确认服务的是最新 `_site/`，而不是旧目录。
4. 强制刷新浏览器，清除旧 Pages/CDN 缓存。

如果鼠标移动时出现上下变化，先检查 `motion.matrixDelta[*][5]`。非零值表示原页面对水平输入确实产生 Y 输出，前端应按原值回放；若 manifest 中始终为零但页面仍漂移，再检查 CSS animation、position 或旧缓存。程序不会自行添加 Y。

## 11. GitHub Actions 抓取结果与本地不同

这是可能的环境差异：

- 出口 IP 和地理位置不同
- Cookie/profile 不同
- A/B 分流不同
- CDN 网络路径不同

工作流明确使用临时 profile 和 `BANNER_TIMEZONE=Asia/Shanghai`，但不能保证与个人电脑显示完全一致。需要个人网络环境时，在 Windows/NAS 抓取后提交 `data/`。

## 12. `data/diagnostic.json` 如何处理

该文件默认被 `.gitignore` 忽略，并可能被下一次失败覆盖。排障时先复制一份：

```text
data/diagnostic.json → 临时目录
```

重点查看 `reason`、`url`、`title`、元素数量以及 `before`/`after`。不要把包含不必要页面信息的诊断文件直接发布到公开站点。

## 13. 数据目录或权限问题

程序默认写入项目根目录的 `data/`。需要把历史放到独立磁盘时：

```powershell
$env:BANNER_DATA_DIR = 'D:\bilibili-banner-data'
python backend\capture.py
```

```bash
export BANNER_DATA_DIR=/volume1/bilibili-banner-data
python backend/capture.py
```

确认运行用户对该目录有创建、替换和写入权限；同时确保构建时 `build_site.py` 使用的是项目默认 `data/`。如果数据放在外部目录，构建脚本不会自动把它复制到 `_site/`，需要将数据目录同步回项目或调整构建流程。

## 14. `data/` 已变化但 git push 失败

典型表现是 `Commit new unique banner` 中出现 `403`、`Permission to ... denied` 或 `GH006`。

按顺序检查：

1. `Settings → Actions → General → Workflow permissions` 是否选择了 `Read and write permissions`，并点击 `Save`。
2. `daily-update.yml` 的更新 job 是否仍有 `contents: write`；不要只修改部署 job。
3. `main` 是否受分支保护规则限制，是否禁止 GitHub Actions 直接 push。若有保护规则，应允许该自动化方式，或改用人工提交数据。
4. 这次运行失败后，远端通常仍保留旧数据；修正权限后重新运行即可。不要为了绕过权限把 token 写进仓库文件。

如果日志显示 `nothing to commit`，这是正常的 no-op，不是 push 故障。

## 15. GitHub Pages 404、JS/CSS/图片 404 或历史为空

先确认 `Settings → Pages → Build and deployment → Source` 是 `GitHub Actions`，并且最近一次 `Deploy GitHub Pages` 为绿色。然后检查：

- 仓库默认分支确实是 `main`；`pages.yml` 的 push 触发器只监听 `main`。
- artifact 根目录直接包含 `index.html`、`app.js`、`interaction.js`、`style.css`、`.nojekyll`、`assets/` 和 `data/`，没有多套一层项目目录。
- `_site/data/index.json` 中的 `records` 是否为空；为空时页面没有历史是数据事实，不是前端加载失败。
- `_site/data/archive/<id>/banner.json` 是否存在，manifest 中每个 `file` 是否在同一归档目录存在。
- 页面地址是否包含仓库名：`https://<用户名>.github.io/<仓库名>/`。当前前端使用相对路径，不能把源文件改成以 `/` 开头的绝对仓库根路径。

资源刚更新后先等待 Pages 部署完成，再用 `Ctrl+F5`；必要时在开发者工具 Network 中确认 404 的准确路径。

## 16. 页面显示静态图、没有交互或出现截图

- 新 manifest 优先看 `type[]`；只有 `type: ["static"]` 才能确认是单静态资源。`layered/video/animated/interactive` 可组合，`completeness: partial` 表示还原不完整。
- v10 可采样交互应看到非空 `layers`、`interaction.model: bilibili-sampled-horizontal-v1` 和非空 `interaction.effects`；v9.2 历史才检查非零 `a`。
- 当前 `capture.py` 不调用截图 API，`app.js` 在加载失败时显示错误，不会显示 `preview.png`。若公网仍出现截图，检查是否部署了旧 Pages artifact、旧 `_site/` 或浏览器缓存，并检查发布物中是否存在 `preview.png`。
- 不要手工把截图改名为 `static.*`；`static.*` 必须是页面引用的原始图片。

## 17. 同一 Banner 被重复归档

正常运行时去重使用资源、结构和交互三段哈希组合的 `contentHash`，不使用日期、URL 或时段槽。资源相同但 transform/animation/交互不同是不同版本；三段都相同且同槽再次抓取才完全 no-op。

旧 v9.2 曾使用较弱哈希，因此历史数据中仍可能存在重复目录。新版本的 `--force` 不绕过结构化哈希；`data/index.json` 会在 family 内按 hash 合并变体。需要修复索引时运行 `python backend/capture.py --rebuild-index`，它不会删除物理目录。

## 18. Actions 每 3 小时定时采样没有执行

检查：

1. workflow 文件是否已经提交到默认分支的 `.github/workflows/daily-update.yml`。
2. Actions 页面是否启用该 workflow，仓库是否被暂停或限制 Actions。
3. 当前仓库默认分支是否与 workflow 所在分支一致；定时任务只从默认分支运行。
4. 是否只是延迟：GitHub 的高负载时段可能使 `schedule` 延后，不要把某个固定分钟当成严格启动时间。
5. 公开仓库若超过 60 天没有活动，GitHub 可能自动禁用 scheduled workflows；重新启用 workflow 后再观察下一次运行。

先使用 `Actions → Daily Banner Update → Run workflow` 手工验证，手工成功后再等待定时任务。

## 19. Pages workflow 与 daily workflow 重复触发

每日工作流使用 `GITHUB_TOKEN` 提交数据；GitHub 不会因为这种 token 推送再次触发新的 workflow，因此不会自动递归启动 `pages.yml`。两个 workflow 也使用了不同的 concurrency group。

如果看到两个运行，先区分是人工 push、手工 `workflow_dispatch`，还是普通个人 token/API push；这些情况可能正常触发 `pages.yml`。检查运行页面的 `event`、commit 作者和触发分支，不要仅凭时间接近就判断为递归。
