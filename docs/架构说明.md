# 架构说明

## 1. 总体架构

项目由抓取层、归档层、构建层和展示层组成：

```text
┌──────────────────────────────┐
│ Bilibili 首页 / Wayback 回放    │
│ 真实渲染 DOM / 归档原始媒体     │
└──────────────┬───────────────┘
               │ Playwright headless
               ▼
┌──────────────────────────────┐
│ capture.py / wayback_import.py │
│ DOM 读取 · 运动测量 · 下载     │
│ 指纹去重 · manifest/index      │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ data/                         │
│ current/ · archive/ · index   │
└──────────────┬───────────────┘
               │ scripts/build_site.py
               ▼
┌──────────────────────────────┐
│ _site/                        │
│ frontend + data + .nojekyll   │
└──────────────┬───────────────┘
               │ HTTP 静态文件
               ▼
┌──────────────────────────────┐
│ 浏览器                        │
│ 筛选 · 懒加载 · 本地分层交互   │
└──────────────────────────────┘
```

展示阶段不请求 Bilibili；所有 Banner 素材必须已经在 `data/` 中。

## 2. 模块职责

### `backend/capture.py`

负责：

- 初始化时间、数据目录、浏览器和 profile。
- 以固定视口访问 `BANNER_SOURCE_URL`。
- 读取 `.animated-banner` 几何信息和 `.layer.firstElementChild`。
- 下载图层媒体和原始静态图。
- 从左右两侧进行 9 点水平输入采样，读取每层真实 matrix/opacity 响应和离场回位曲线。
- 生成 `banner.json`，计算 `contentHash`。
- 计算 `layoutHash`，将同日同结构素材归入同一 `familyId`，记录 3 小时 `observedSlots`。
- 替换 `data/current/`，必要时复制 `data/archive/`。
- 从历史 manifest 重建 `data/index.json`。
- 在关键结构异常时写 `data/diagnostic.json`。

它不负责：

- 生成截图。
- 启动可见浏览器窗口。
- 运行前端页面。
- 删除旧历史目录。

### `backend/wayback_import.py`

负责：

- 从 2018 年开始按月、周或日调用 Wayback Availability API 发现首页快照。
- 始终以 headless Chromium 打开回放页，复用 `capture.py` 的图层测量、素材哈希、归档和索引函数。
- 将原始素材地址改写为 Wayback 时间戳资源，并阻止浏览器直接访问 Bilibili/HDslb。
- 识别当前 Header 和旧版 `.head-banner`、`.header-banner`、`#banner_link`、`.banner_link` 的真实图片或背景图。
- 以 `observations` 保存同一素材的多次历史出现，不复制物理素材。

它不会覆盖 `data/current/`，不会生成截图；快照缺少素材或分层互动无法执行时只报告失败。

### `data/`

是抓取器和前端之间的文件协议：

- `current/`：最近一次被接受的唯一内容副本；相同素材不会替换资源，仅在新时段/旧模型升级时同步 manifest 元数据。
- `archive/`：去重后的历史物料；一个 manifest 可通过 `observations` 被多个历史日期引用。
- `index.json`：前端只用来列出历史和定位 manifest。
- `diagnostic.json`：本地排障信息，不属于发布数据。

### `frontend/`

负责：

- 加载本地 `data/index.json`。
- 年/月/季节筛选。
- 按需加载 manifest。
- 创建 `split` 或 `static` Banner。
- v10 按 manifest 自带的 matrix/opacity/回位采样曲线插值；v9.2 继续使用 `a`。
- 按上海时区从一个 Banner 家族的 `variants` 中选择最近观测时段，并在页面打开期间自动切换。

它不负责：

- 访问 Bilibili。
- 下载远程 CDN 素材。
- 服务端去重或修改数据。

### `scripts/build_site.py`

将 `index.html`、`app.js`、`interaction.js`、`style.css`、`assets/` 和 `data/` 复制到 `_site/`，排除 `preview.png`、`diagnostic.json`、`.capture_*` 和 `.current_old`，并创建 `.nojekyll`。默认输出目录是项目根目录 `_site/`，可用 `--output` 覆盖。

### `scripts/serve.py`

使用 Python 标准库 `ThreadingHTTPServer` 提供静态文件服务，默认目录 `_site/`、端口 `8765`。它只负责开发预览，不参与抓取和发布。

## 3. 抓取时序

```text
启动 capture.py
    │
    ├─ 读取 BANNER_* / BROWSER_EXE 配置
    ├─ 启动 persistent context（headless=True）
    ├─ 导航首页两次，等待 DOM 初始化
    ├─ 读取 .animated-banner geometry
    ├─ 读取分层结构
    ├─ 读取静态原图并下载
    ├─ 从左右两侧采样 9 个水平差值
    ├─ 读取每层 matrix/opacity 曲线
    ├─ 鼠标离场并采样真实回位曲线
    ├─ 下载分层媒体
    ├─ 生成 manifest + contentHash + layoutHash + familyId
    ├─ 与 current/archive hash 比较
    ├─ 重复且同槽 → 完全无操作
    ├─ 重复但新槽/旧模型 → 只更新已有 manifest/index
    ├─ 新内容 → 替换 current、新增 archive、重建 index.json
    └─ 清理临时目录和临时 profile
```

关键失败边界：

```text
缺少 .animated-banner       → diagnostic + 失败
探测前后图层数变化           → diagnostic + 失败
所有采样 matrix/opacity 效果均为 0 → diagnostic + 失败
检测到动态 Y 位移             → diagnostic + 失败
图层 URL 缺失或素材下载失败   → diagnostic + 失败
无可用分层但有静态原图        → static manifest
```

## 4. 交互数据流

后台不复制或执行归档后的 Bilibili 远程脚本，而是记录其 JS 在真实 DOM 上产生的可观察输出：

```text
后台：inputSamplesPx = [-D ... 0 ... +D]
      motion[layer][sample] = computed state - baseline state
      return[layer][time] = effectRemaining

前端：moveX = currentClientX - enterClientX
      effect = piecewiseLinear(inputSamplesPx, motion, moveX)
      leaveEffect = capturedEffect × sampledReturnRemaining
```

前端使用 `[a,b,c,d,e,f]` matrix：

```text
初始 matrix  →  保留原始布局
鼠标移动     →  插值 matrix 前五项和 opacity，matrix[5] 始终保持原始 Y
鼠标离开     →  使用该 Banner 自己的 returnSamplesMs/returnRemaining
```

因此“水平交互”既表示输入只来自 X，也表示动态 Y 被拒绝；原始 matrix 本身仍可有固定 Y。

## 5. 去重和索引关系

```text
归档文件 bytes
    ↓ SHA-256
稳定的 entries（图层顺序 + 类型 + 尺寸）
    ↓ SHA-256 前 24 位
contentHash
    ↓
archive/<timestamp>_<contentHash>/
    ↓ 扫描 banner.json
index.json（capturedAt 倒序 + contentHash 去重）
```

`contentHash` 不包含日期、远程 URL、初始 matrix、采样曲线或时段元数据。这保证同样素材永不重复归档。不同实际素材可通过同一 `familyId` 作为时段变体展示；新观测槽只更新 manifest/index。

## 6. 部署边界

### GitHub Actions / Pages

```text
.github/workflows/daily-update.yml
    ├─ 定时/手工触发
    ├─ 在 Runner 上 headless 抓取
    ├─ 有 data 变化才 commit/push
    └─ 构建并 deploy Pages

.github/workflows/pages.yml
    └─ 前端/数据/构建脚本变化时只构建并 deploy Pages
```

`.github/` 是平台自动化层，不被核心代码依赖。核心运行单元是 `backend/`、`frontend/`、`data/` 和 `scripts/build_site.py`。

### NAS

```text
cron/任务计划
    → backend/capture.py
    → scripts/build_site.py
    → Nginx/Caddy
```

NAS 不需要 GitHub Actions；可将 `data/` 放到独立卷。但当前 `build_site.py` 的数据源常量是项目根目录 `data/`，若外部数据目录未同步回该位置，构建不会自动带上外部历史。

## 7. 资源和状态边界

| 状态/资源 | 生产者 | 消费者 | 生命周期 |
| --- | --- | --- | --- |
| `.runtime/browser-profile` | capture | Playwright | 本地持久化，可删除后重新创建 |
| 临时 `.capture_*` | capture | capture | 单次运行，结束清理 |
| `data/current/` | capture | 人工检查/迁移 | 最近一次被接受的唯一内容 |
| `data/archive/` | capture | index/build/frontend | 长期历史，不自动删除 |
| `data/index.json` | capture | frontend | 每次新归档或重建时更新 |
| `data/diagnostic.json` | capture | 人工排障 | 失败时覆盖，默认忽略 |
| `_site/` | build_site | serve/Pages | 构建产物，可重建 |

## 8. 当前未实现的扩展

架构目前没有实现：

- 数据库或对象存储适配器。
- 多来源或多用户归档。
- 自动清理、压缩或 Git LFS 管理。
- 动态 CSS filter、Canvas/WebGL 或无法由分层 DOM computed style表达的效果。
- 基于图像语义识别 Banner 家族；当前自动规则是“同日 + 同布局结构”。
- 抓取任务锁和失败重试队列。

新增这些能力时，应保持 `data/index.json`、`banner.json` 和本地相对资源路径的兼容，避免前端与部署平台耦合。
