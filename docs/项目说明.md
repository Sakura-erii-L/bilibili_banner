# Bilibili Banner Archive 项目说明

## v11 API-first 更新（2026-08-31）

当前 Banner 的默认抓取入口已改为 `python backend/capture.py` 直接请求 Bilibili Header API，并以 `split_layer.layers[].resources[]` 为权威结构。默认路径不启动浏览器；`--verify-dom` 只做隐藏 DOM 校验，`--legacy-dom-capture` 才启用旧完整采样。历史导入采用本地 archive → Wayback Header API/CDX → palxiao → HTTP HTML/CSS，默认不启动浏览器。详细实现见 `docs/API_FIRST_ARCHITECTURE.md`。

## 1. 文档范围

本文档以当前目录中的代码、工作流和 `data/` 实际内容为准，描述 v11 的已实现行为。旧版本的修复背景见：

- [v9.1 抓取与交互说明](v9.1抓取与交互.md)
- [v9.2 截图回退修复](v9.2截图回退修复.md)

历史数据已重置，只保留 `2026-08-30` 的真实分层 archive 作为基线；其余日期由自动任务从 `2019-08-01` 起重新采集。回填期间数量会持续变化，应以 `data/index.json` 和归档审计结果为准。

## 2. 项目目标

项目用于长期保存 Bilibili 首页顶部 Banner 的历史版本，并尽可能保留原网站的静态、分层、视频、动画和交互构成。

目标不是每天保存一张截图，而是保存可被前端重新组合的本地素材和必要的布局/交互元数据：

```text
Bilibili 首页真实渲染
        ↓
读取 .animated-banner .layer
        ↓
下载每个图层的原始素材
        ↓
多点采样鼠标水平输入造成的 matrix/opacity 和回位变化
        ↓
保存素材、初始状态、交互曲线、时段槽和 manifest
        ↓
前端从本地归档重建 Banner
```

## 3. 已实现功能

### 3.1 当前 Header API 抓取

`backend/capture.py` 默认直接请求 Header API，不启动浏览器。`--verify-dom` 只做隐藏 DOM 校验，`--legacy-dom-capture` 才启动 Playwright 并执行旧的完整 DOM 采样。

默认配置：

| 项目 | 当前值 |
| --- | --- |
| 来源 | `https://www.bilibili.com/` |
| 时区 | `Asia/Shanghai` |
| 视口 | `1650 × 800` |
| locale | `zh-CN` |
| 等待分层/静态图的最长时间 | `18000ms`，之后仍会额外等待 `1800ms` |
| 运动探测距离 | 最多 `1000px`，同时至少按 Banner 宽度保留 `200px` |
| 运动结算等待 | `1200ms` |

浏览器 profile 行为（仅 DOM 校验/legacy 模式）：

- 普通本地运行使用 `BANNER_PROFILE_DIR`，默认是项目根目录的 `.runtime/browser-profile`，便于保留站点运行所需的浏览器状态。
- 设置 `CI` 或 `BANNER_PROFILE_MODE=temporary` 时使用临时目录，任务结束后删除。
- 即使使用持久化 profile，浏览器仍然是 headless；profile 的持久化不等于显示浏览器窗口。

在 DOM 校验/legacy 模式中，页面会执行两次 `domcontentloaded` 导航以提高首页动态内容初始化的成功率，然后等待以下任一条件：

```text
.animated-banner .layer 数量大于 0
picture.banner-img img 存在
.bili-header__banner img 存在
```

程序随后从 `.animated-banner`、`.bili-header__banner`、`.head-banner`、`.bili-banner` 等候选中读取几何信息。所有支持容器都不存在时才写诊断并失败。

### 3.2 分层 DOM 读取

每一个 `.animated-banner .layer` 的读取逻辑如下：

```text
.layer
└─ firstElementChild       ← 读取初始 transform 的目标
   └─ img/video             ← 下载的媒体，可以是目标本身或嵌套元素
```

程序记录：

- `tag`、`src`、`contentType`
- CSS/DOM 推导出的 `width`、`height`
- `naturalWidth`、`naturalHeight`
- `objectFit`、`objectPosition`、`transformOrigin`
- 目标元素的二维 CSS matrix `[a,b,c,d,e,f]`
- 图层与媒体的透明度

如果媒体 URL 是普通 HTTP(S) 地址，使用 Playwright request context 下载并携带页面来源和固定 User-Agent；如果是 `blob:` 地址，则在页面内 `fetch()` 为二进制后保存到磁盘。文件扩展名优先取 URL，其次根据 `Content-Type` 推导。

### 3.3 交互效果采样（legacy DOM 模式）

只有 `--legacy-dom-capture` 才会采样网站 JS 对真实 DOM 造成的输出；默认 Header API 路径直接保存官方交互参数：

1. 分别从 Banner 左右边缘进入。
2. 在同一 Y 坐标覆盖负向、零点和正向共 9 个水平差值。
3. 每个点读取 computed matrix、图层透明度和媒体透明度。
4. 选择效果最强的采样点，鼠标离场后按多个毫秒时间点读取剩余效果。

v10 保存：

```text
inputSamplesPx ↔ motion.matrixDelta / opacityDelta
returnSamplesMs ↔ motion.returnRemaining
```

前端在相邻输入点间插值，因此不同 Banner 可以拥有不同的非线性曲线、matrix/opacity 效果和回位节奏。`a` 仍作为旧前端兼容斜率生成，但 v10 前端不依赖它。

抓取保护：

- 探测前后图层数量改变：写诊断并中止。
- 所有 matrix/opacity 采样效果均为零：保留真实图层，交互标记为 none/partial，不伪造统一移动参数。
- 完整保存采样到的二维 matrix；不会人为制造 Y，但原页面由水平输入实际产生的 Y/scale/rotate 会保留。
- 图层缺少素材 URL 或下载失败时保留其它真实图层，并在 `completeness: partial`、`missing_assets[]` 中明确记录。

### 3.4 静态模式

程序只在证据表明 Banner 是单一媒体时把原始资源保存为 `static.*`。检测到 `is_split_layer`、多个媒体或 `.layer` 时，第一张 IMG 不会被当成完整 Banner；可恢复部分结构时保存 partial layers，原始 `pic/static` 仅作为 fallback。

这里的静态图是 Bilibili 页面引用的原始图片，不是浏览器截图。若没有单图但存在 video/SVG/canvas 等复杂证据，程序保存可恢复资源或 metadata-only partial，而不是伪造 static。

### 3.5 内容去重与历史归档

分层模式对每个实际下载文件计算 SHA-256，再按图层顺序组合这些信息：

```text
index + tag + 文件 SHA-256 + 文件大小 + naturalWidth + naturalHeight
        ↓
JSON（稳定排序和紧凑序列化）
        ↓
SHA-256 前 24 位
        ↓
contentHash
```

新版本分别计算 `resourceHash`、`structureHash` 和 `interactionHash`，再组合为 `contentHash`。以下因素不进入 `contentHash`：

- 抓取日期和时间
- CDN URL、查询参数
- `familyId` 和观测时段槽
- 浏览器运行元数据

因此：

```text
当天内容首次出现       → 更新 current，新增 archive，并重建 index
相同素材且时段已记录   → 完全跳过，不改 data
相同素材但出现新时段   → 只更新已有 manifest/index，不新增 archive
历史 v9.2 素材再次出现 → 原地升级真实交互元数据，不新增 archive
```

`data/current/` 会保存最近一次被接受的唯一内容工作副本。首次出现的新内容会复制到：

```text
data/archive/YYYY-MM-DD_HHMMSS_<contentHash>/
```

然后 `rebuild_index()` 重新扫描所有 manifest，按 `familyId` 聚合时段变体、按 `contentHash` 去重素材，并按抓取时间倒序排列。

`--force` 只强制刷新已有素材的交互元数据，不再允许创建相同 `contentHash` 的重复物理归档。

### 3.6 前端历史画廊

前端位于 `frontend/`，构建后作为纯静态站点发布：

1. 从 `./data/index.json` 读取历史索引。
2. 生成年份和月份选项；季节选项固定为春、夏、秋、冬。
3. 根据组合筛选结果按索引顺序创建历史条目。
4. 用 `IntersectionObserver`（提前 `900px`）加载即将进入视口的 manifest。
5. 一个 `familyId` 只创建一个条目，按 `Asia/Shanghai` 当前时间选择最近 `observedSlots` 的变体。
6. `split` 使用本地图层重新组合；`static` 使用 `static.*`；页面每分钟检查时段切换。

分层重建时，前端：

- 恢复 manifest 中的初始 matrix、尺寸、`objectFit`、`objectPosition` 和透明度。
- 在视口宽度大于抓取视口时按比例补偿 X/Y 初始位移和媒体尺寸。
- 对视频设置 `autoplay`、`loop`、`muted`、`playsInline`。
- 鼠标进入时记录 `clientX`，移动时按该 manifest 自己的采样曲线插值完整六项 matrix 和 opacity。
- 鼠标离开后按采样到的 `returnSamplesMs` 回位；v9.2 才使用固定时长和 `a` 回退。

前端不会：

- 请求 Bilibili 页面或 CDN URL
- 生成或显示截图
- 在分层 manifest 加载失败时显示 `preview.png`
- 动态修改 Y、CSS filter 或 blur；scale、rotate 和 opacity 仅在抓取曲线实际记录到变化时回放

### 3.7 静态站点构建

`scripts/build_site.py` 会：

1. 删除并重建输出目录（默认 `_site/`）。
2. 复制 `frontend/index.html`、`frontend/app.js`、`frontend/interaction.js`、`frontend/style.css` 和 `frontend/assets/`。
3. 复制整个 `data/`，但忽略旧历史中的 `preview.png`、失败诊断 `diagnostic.json`、抓取临时目录 `.capture_*` 和替换备份 `.current_old`。
4. 写入空的 `_site/.nojekyll`。

因此旧归档即使残留截图或本地运行时文件，也不会将它们发布到 Pages；新程序本身也不会生成截图。

## 4. 运行流程

### 4.1 本地一次更新

```text
安装 Python 依赖（只有 DOM 校验/legacy 时才需要浏览器）
        ↓
python backend/capture.py
        ↓
临时目录中下载、生成 banner.json、计算 contentHash
        ↓
与 current/archive 的 contentHash 比较
        ├─ 重复同槽 → 完全无操作
        ├─ 重复新槽/旧模型 → 更新已有 manifest/index
        └─ 新内容 → 替换 current、复制 archive、重建 index.json
        ↓
python scripts/build_site.py
        ↓
python scripts/serve.py
```

抓取使用临时目录完成大部分工作，正常失败不会主动清理既有历史 archive。诊断文件写入 `data/diagnostic.json`，该文件默认被 `.gitignore` 忽略。

### 4.2 GitHub Actions

```text
daily-update.yml（默认北京时间每 3 小时第 17 分钟或手工运行）
        ↓
Python 3.12 + Header API
        ↓
CI 临时 profile + headless capture.py
        ↓
若 data 改变则 commit/push
        ↓
build_site.py
        ↓
GitHub Pages artifact + deploy-pages
```

`pages.yml` 可在前端、数据、构建脚本或工作流变化时重新构建和部署；两份工作流均要求 Pages 的 Source 使用 `GitHub Actions`。

### 4.3 NAS

NAS 只需要运行核心代码：

```text
任务计划/cron
        ↓
backend/capture.py
        ↓
scripts/build_site.py
        ↓
Nginx/Caddy 指向 _site/
```

NAS 不需要 `.github/`。将 `data/` 单独放到持久化卷并通过 `BANNER_DATA_DIR` 指向它，可以独立更新程序代码而不影响历史。

### 4.4 Wayback 历史回填

`backend/wayback_import.py` 是独立的一次性/分批任务，不进入每日实时抓取主流程。它从 `2019-08-01` 开始发现 Wayback 快照，按 Wayback Header API/CDX → 精确日期 palxiao → HTTP HTML/CSS 恢复，只下载归档中真实存在的图层、图片、视频或旧版 CSS 背景图，并复用 `capture.py` 的哈希、归档和索引实现。没有任何成功保存的主素材时，该快照只记录为失败，不创建 archive。

历史导入不会替换 `data/current/`。同一素材跨日期出现时写入 `observations`，让多个日期记录引用同一个物理 archive。palxiao 的 `assets/YYYY-MM-DD` 仅代表其 `observedAt`，不推断 `effectiveFrom`；真实视频源优先于 poster。详细命令和 GitHub Actions 操作见 `docs/Wayback历史导入.md`。

## 5. 当前限制和风险

以下是当前实现的限制，不是已实现功能：

- 抓取依赖 Bilibili 的当前 DOM 选择器和网络可用性；DOM 改版、验证码、登录状态或 A/B 分流可能导致数据不同或抓取失败。
- 视口固定为 `1650 × 800`（可通过环境变量调整），不同运行环境可能看到不同 Banner 和不同几何尺寸。
- `contentHash` 包含资源、结构、动画和交互配置；相同素材但动态参数不同会保存为不同版本。
- 素材下载采用逐层请求；缺失项会形成 partial 归档，不会合成或伪装为 static。
- 没有数据库或自动清理策略；会写入 `data/` 的 Daily Update 与历史导入 workflow 共用不可取消的并发组，部署者仍应避免本地同一数据目录上的抓取任务重叠，并定期备份/清理历史。
- GitHub Actions 的网络环境不等同于本地网络；若对来源一致性敏感，应使用本地/NAS 抓取。
- Wayback 可能缺少历史子资源或脚本；不可恢复的快照会跳过，不会通过截图或当前站点素材补齐。palxiao 只提供独立结构化复现数据，不是官方 `split_layer`，其日期不等于生效日期。

## 6. 不属于当前实现的计划项

当前代码没有实现以下能力，文档不将它们当作现有功能：

- 自动删除或压缩旧归档
- 数据库/对象存储后端
- 多来源 Banner 对比
- CSS filter、3D perspective matrix、Canvas/WebGL shader 等尚不能完整序列化的效果；程序保存证据并标记 partial
- 使用图像语义自动判断 Banner 家族；当前规则是同日且布局结构相同
- 从 GitHub Actions 以外的服务自动获取本地浏览器看到的内容

## 7. 维护建议

- Bilibili DOM 改版后，先检查 `data/diagnostic.json`、`backend/capture.py` 中的选择器和抓取日志，再修改前端。
- 只改变 UI 时运行 `python scripts/build_site.py`；改变抓取或数据结构后至少执行一次抓取/索引检查。
- 不要手工修改已有 `banner.json` 的 `contentHash`，除非同步重算文件指纹。
- 迁移机器时优先复制 `data/`，不要只复制 `_site/`；`_site/` 可以随时重新生成。
- 发布前用 HTTP 服务检查 `data/index.json`、manifest 路径和图层资源是否可访问。
