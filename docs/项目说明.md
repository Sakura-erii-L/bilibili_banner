# Bilibili Banner Archive 项目说明

## 1. 文档范围

本文档以当前目录中的代码、工作流和 `data/` 实际内容为准，描述 v9.2 的已实现行为。旧版本的修复背景见：

- [v9.1 抓取与交互说明](v9.1抓取与交互.md)
- [v9.2 截图回退修复](v9.2截图回退修复.md)

当前仓库样例在 2026-08-30 生成，`data/index.json` 中有 1 条唯一历史记录：`split` 模式、28 个图层。后续运行会改变这个数量，文档中的动态数量不应替代对 `data/index.json` 的检查。

## 2. 项目目标

项目用于长期保存 Bilibili 首页顶部 Banner 的历史版本，并尽可能保留原网站分层 Banner 的水平视差效果。

目标不是每天保存一张截图，而是保存可被前端重新组合的本地素材和必要的布局/交互元数据：

```text
Bilibili 首页真实渲染
        ↓
读取 .animated-banner .layer
        ↓
下载每个图层的原始素材
        ↓
测量鼠标水平移动造成的 X 轴变化
        ↓
保存素材、初始 matrix、a 和 manifest
        ↓
前端从本地归档重建 Banner
```

## 3. 已实现功能

### 3.1 Headless 浏览器抓取

`backend/capture.py` 使用 Playwright 的 Chromium API，固定以 `headless=True` 启动持久化浏览器上下文。程序不会打开可见的 Edge、Chrome 或 Bilibili 窗口。

默认配置：

| 项目 | 当前值 |
| --- | --- |
| 来源 | `https://www.bilibili.com/` |
| 时区 | `Asia/Shanghai` |
| 视口 | `1650 × 800` |
| locale | `zh-CN` |
| 等待分层/静态图的最长时间 | `18000ms`，之后仍会额外等待 `1800ms` |
| 运动探测距离 | 最多 `1000px`，同时至少按 Banner 宽度保留 `200px` |
| 运动结算等待 | `1200ms` |

浏览器 profile 行为：

- 普通本地运行使用 `BANNER_PROFILE_DIR`，默认是项目根目录的 `.runtime/browser-profile`，便于保留站点运行所需的浏览器状态。
- 设置 `CI` 或 `BANNER_PROFILE_MODE=temporary` 时使用临时目录，任务结束后删除。
- 即使使用持久化 profile，浏览器仍然是 headless；profile 的持久化不等于显示浏览器窗口。

页面会执行两次 `domcontentloaded` 导航以提高首页动态内容初始化的成功率，然后等待以下任一条件：

```text
.animated-banner .layer 数量大于 0
picture.banner-img img 存在
.bili-header__banner img 存在
```

程序随后必须找到 `.animated-banner` 并读取其几何信息。找不到这个容器时，抓取失败并写入 `data/diagnostic.json`；这不是静态模式。

### 3.2 分层 DOM 读取

每一个 `.animated-banner .layer` 的读取逻辑如下：

```text
.layer
└─ firstElementChild       ← 读取初始 transform 的目标
   └─ img/video             ← 下载的媒体，可以是目标本身或嵌套元素
```

程序记录：

- `tag`、`src`、`contentType`
- CSS/DOM 推导出的 `width`、`height`
- `naturalWidth`、`naturalHeight`
- `objectFit`、`objectPosition`、`transformOrigin`
- 目标元素的二维 CSS matrix `[a,b,c,d,e,f]`
- 图层与媒体的透明度

如果媒体 URL 是普通 HTTP(S) 地址，使用 Playwright request context 下载并携带页面来源和固定 User-Agent；如果是 `blob:` 地址，则在页面内 `fetch()` 为二进制后保存到磁盘。文件扩展名优先取 URL，其次根据 `Content-Type` 推导。

### 3.3 交互参数测量

当抓到至少一个分层时，程序执行一次与网站交互逻辑对应的水平探测：

1. 将鼠标移动到 Banner 左侧内部。
2. 在相同 Y 坐标上向右移动探测距离 `D`。
3. 等待 `1200ms`，让 Bilibili 自己的脚本更新 `firstElementChild.style.transform`。
4. 再次读取每层的 X 位移。

每层系数为：

```text
a = (after.transformX - before.transformX) / D
```

`a` 的含义：

- 正负号表示相对鼠标移动方向。
- 绝对值表示移动速度的相对强弱。
- `a = 0` 表示该层不随探测移动。

抓取保护：

- 探测前后图层数量改变：写诊断并中止。
- 至少有一个图层下载成功，且所有带媒体地址的被测图层的最大 `abs(a)` 不超过 `1e-6`：写诊断并中止，不归档一个无交互结果。
- 图层缺少素材 URL 或任一素材下载失败时写入 `data/diagnostic.json` 并中止本次归档，避免保存缺层的 `split` 结果；这不是截图回退。

### 3.4 静态模式

程序每次都会尝试读取 Bilibili 原始静态头图，并将它保存为 `static.*`。当页面没有可用分层 DOM 时，manifest 的 `mode` 为 `static`，前端直接显示该原始静态图片；如果页面已经提供分层但素材 URL 缺失或下载失败，程序会失败而不会降级为不完整的静态或分层归档。

这里的静态图是 Bilibili 页面引用的原始图片，不是浏览器截图。若 `.animated-banner` 容器本身不存在，程序会失败，不会绕过结构错误生成静态归档。

### 3.5 内容去重与历史归档

分层模式对每个实际下载文件计算 SHA-256，再按图层顺序组合这些信息：

```text
index + tag + 文件 SHA-256 + 文件大小 + naturalWidth + naturalHeight
        ↓
JSON（稳定排序和紧凑序列化）
        ↓
SHA-256 前 24 位
        ↓
contentHash
```

静态模式只对静态文件计算同样的内容指纹。以下因素不进入 `contentHash`：

- 抓取日期和时间
- CDN URL、查询参数
- 初始 transform matrix
- 水平运动系数 `a`
- 浏览器运行元数据

因此：

```text
当天内容首次出现       → 更新 current，新增 archive，并重建 index
当天内容与 current 相同 → 完全跳过，不改 data
历史中已有但本次回归   → 完全跳过，不改 current、archive、index
```

`data/current/` 会保存最近一次被接受的唯一内容工作副本。首次出现的新内容会复制到：

```text
data/archive/YYYY-MM-DD_HHMMSS_<contentHash>/
```

然后 `rebuild_index()` 重新扫描所有 manifest，按 `capturedAt` 倒序排列，并按 `contentHash` 再去重。程序不会自动删除重复的物理目录。

`--force` 会绕过当前内容和历史内容的重复判断，创建新的物理归档目录；这适合人工保留一次重新抓取结果，但会增加磁盘/Git 体积，索引仍只保留同一 `contentHash` 的一条记录。

### 3.6 前端历史画廊

前端位于 `frontend/`，构建后作为纯静态站点发布：

1. 从 `./data/index.json` 读取历史索引。
2. 生成年份和月份选项；季节选项固定为春、夏、秋、冬。
3. 根据组合筛选结果按索引顺序创建历史条目。
4. 用 `IntersectionObserver`（提前 `900px`）加载即将进入视口的 manifest。
5. `split` 使用本地图层重新组合；`static` 使用 `static.*`。

分层重建时，前端：

- 恢复 manifest 中的初始 matrix、尺寸、`objectFit`、`objectPosition` 和透明度。
- 在视口宽度大于抓取视口时按比例补偿 X/Y 初始位移和媒体尺寸。
- 对视频设置 `autoplay`、`loop`、`muted`、`playsInline`。
- 鼠标进入时记录 `pageX`，移动时按每层 `a` 修改 matrix 的 X 分量。
- 始终保留初始 matrix 的 Y 分量，鼠标离开后在 `returnDurationMs`（当前 `300ms`）内回位。

前端不会：

- 请求 Bilibili 页面或 CDN URL
- 生成或显示截图
- 在分层 manifest 加载失败时显示 `preview.png`
- 动态修改 Y、scale、rotate、opacity 或 blur

### 3.7 静态站点构建

`scripts/build_site.py` 会：

1. 删除并重建输出目录（默认 `_site/`）。
2. 复制 `frontend/index.html`、`frontend/app.js`、`frontend/style.css`。
3. 复制整个 `data/`，但忽略旧历史中的 `preview.png`、失败诊断 `diagnostic.json`、抓取临时目录 `.capture_*` 和替换备份 `.current_old`。
4. 写入空的 `_site/.nojekyll`。

因此 v9.2 即使旧归档残留截图或本地运行时文件，也不会将它们发布到 Pages；新程序本身也不会生成截图。

## 4. 运行流程

### 4.1 本地一次更新

```text
安装 Python 依赖和浏览器
        ↓
python backend/capture.py
        ↓
临时目录中下载、生成 banner.json、计算 contentHash
        ↓
与 current/archive 的 contentHash 比较
        ├─ 重复 → 完全无操作
        └─ 新内容 → 替换 current、复制 archive、重建 index.json
        ↓
python scripts/build_site.py
        ↓
python scripts/serve.py
```

抓取使用临时目录完成大部分工作，正常失败不会主动清理既有历史 archive。诊断文件写入 `data/diagnostic.json`，该文件默认被 `.gitignore` 忽略。

### 4.2 GitHub Actions

```text
daily-update.yml（默认每天北京时间 06:17 或手工运行）
        ↓
Python 3.12 + Playwright Chromium
        ↓
CI 临时 profile + headless capture.py
        ↓
若 data 改变则 commit/push
        ↓
build_site.py
        ↓
GitHub Pages artifact + deploy-pages
```

`pages.yml` 可在前端、数据、构建脚本或工作流变化时重新构建和部署；两份工作流均要求 Pages 的 Source 使用 `GitHub Actions`。

### 4.3 NAS

NAS 只需要运行核心代码：

```text
任务计划/cron
        ↓
backend/capture.py
        ↓
scripts/build_site.py
        ↓
Nginx/Caddy 指向 _site/
```

NAS 不需要 `.github/`。将 `data/` 单独放到持久化卷并通过 `BANNER_DATA_DIR` 指向它，可以独立更新程序代码而不影响历史。

## 5. 当前限制和风险

以下是当前实现的限制，不是已实现功能：

- 抓取依赖 Bilibili 的当前 DOM 选择器和网络可用性；DOM 改版、验证码、登录状态或 A/B 分流可能导致数据不同或抓取失败。
- 视口固定为 `1650 × 800`（可通过环境变量调整），不同运行环境可能看到不同 Banner 和不同几何尺寸。
- `contentHash` 不包含 matrix 和运动系数；相同素材但不同动态参数会被视为同一内容。
- 素材下载采用逐层请求；任一分层 URL 缺失或 CDN 请求失败都会写诊断并中止，不会归档不完整的真实分层。
- 没有数据库、任务锁、后台 API 或自动清理策略；部署者应避免同一数据目录上的抓取任务重叠，并定期备份/清理历史。
- GitHub Actions 的网络环境不等同于本地网络；若对来源一致性敏感，应使用本地/NAS 抓取。

## 6. 不属于当前实现的计划项

当前代码没有实现以下能力，文档不将它们当作现有功能：

- 自动删除或压缩旧归档
- 数据库/对象存储后端
- 多来源 Banner 对比
- 对 Y 轴、旋转、缩放等复杂动态效果的完整复现
- 从 GitHub Actions 以外的服务自动获取本地浏览器看到的内容

## 7. 维护建议

- Bilibili DOM 改版后，先检查 `data/diagnostic.json`、`backend/capture.py` 中的选择器和抓取日志，再修改前端。
- 只改变 UI 时运行 `python scripts/build_site.py`；改变抓取或数据结构后至少执行一次抓取/索引检查。
- 不要手工修改已有 `banner.json` 的 `contentHash`，除非同步重算文件指纹。
- 迁移机器时优先复制 `data/`，不要只复制 `_site/`；`_site/` 可以随时重新生成。
- 发布前用 HTTP 服务检查 `data/index.json`、manifest 路径和图层资源是否可访问。
